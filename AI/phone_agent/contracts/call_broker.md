# 전화 에이전트 서버 정의 (v0.3.1)

서버가 요청을 어떻게 받고, 언제 전화를 걸고, 결과를 어떻게 정하는지 적은 문서입니다. 요청·결과의 필드는 [인풋·아웃풋](io.md)에 있고, 여기서는 반복하지 않습니다.

> **구현 상태 (2026-11-20)**: 서버 코드가 이 문서대로 동작하고 자동 테스트 115개가 통과합니다. 문의 → 확정 두 번 통화는 live 에이전트로 실제 전화에서 확인했습니다. 등기부 문자 수신과 알림 실제 발송은 아직 확인하지 않았습니다. 아래 '구현 상태' 표에 항목별로 적었습니다.

## API

| 메서드·경로 | 하는 일 | 응답 |
|---|---|---|
| `POST /api/broker-call-batches` | 문의 통화 묶음 접수 | `201` 새 접수, `200` 같은 `approval_id`의 기존 묶음 |
| `GET /api/broker-call-batches/{batch_id}` | 문의 묶음의 진행·결과·중복 후보·알림 | `200`, 없으면 `404` |
| `POST /api/visit-confirmations` | 확정 통화 묶음 접수 | `201`/`200`, 문의 통화·방이 없거나 중개사가 안 된다고 한 시각이면 `409` |
| `GET /api/visit-confirmations/{batch_id}` | 확정 묶음의 진행·결과·알림 | `200`, 없으면 `404` |
| `GET /api/broker-calls/{call_id}` | 통화 한 건(문의·확정 모두) | `200`, 없으면 `404` |
| `GET /api/registry-docs/{message_id}/media/{index}` | 등기부 첨부. 문자로 온 것은 공급사에서 받아 그대로 전달(저장 안 함), 사용자가 올린 PDF는 메모리에서 | `200` 파일, 없으면 `404`, 공급사 오류 `502` |
| `POST /api/broker-calls/{call_id}/registry-docs` | 사용자가 등기부 PDF를 올려 그 문의 통화(`?listing_index=`로 방까지)에 붙임 | `201` 문서, 통화 없음 `404`, PDF 아님·방 없음 `422`, 10MB 넘음 `413` |
| `DELETE /api/registry-docs/{message_id}` | 사실 정리를 마친 뒤 올린 원본 삭제 | `204`, 없거나 문자로 온 것 `404` |
| `GET /api/health` | 모드, 알림 길(`kakao`/`sms`/`log`), MCP·등기부 수신 설정 여부 | `200` |
| `/mcp` | MCP(Streamable HTTP) 입구 `mcp-phone` | |

## 접수

1. 형식을 확인합니다. 맞지 않으면 `422 invalid_request`이고 아무 통화도 만들지 않습니다.
2. 같은 종류(문의/확정)의 묶음에 `approval_id`가 이미 있으면 새로 만들지 않고 기존 묶음을 돌려줍니다.
3. 확정 묶음은 모든 `visits[].call_id`가 끝난 문의 통화이고 그 방(`listing_index`)이 있는지, `at`이 그 통화에서 중개사가 된다고 한 시간(`broker_slots`) 안인지 먼저 봅니다. 하나라도 아니면 요청 전체를 `409`로 거절합니다. 통과하면 `visits`를 문의 통화(사무소)별로 묶어 **사무소마다 확정 통화 한 건**(방 최대 3개)을 만듭니다.
4. 통화를 순서대로 검사합니다. 걸 수 없는 통화는 `status: "rejected"`로 남기고 나머지는 진행합니다.

| `error` | 뜻 | 범위 |
|---|---|---|
| `invalid_request` | 필수 값이 없거나 형식이 맞지 않음 | 요청 전체 (`422`) |
| `not_allowed` | 시연 모드인데 허용 번호가 설정되지 않음 | 요청 전체 (`409`) |
| `call_not_found`, `listing_not_found` | 확정할 문의 통화나 방이 없음 | 요청 전체 (`409`) |
| `outside_broker_slots` | `at`이 문의 통화에서 중개사가 된다고 한 시간 밖. `detail`에 그 방과 `broker_slots` | 요청 전체 (`409`) |
| `already_called_today` | 같은 등록번호에 그날 이미 문의 전화함 | 그 사무소만 |
| `daily_limit` | 그날 문의 10통을 다 씀(서버 전체) | 그 사무소부터 뒤쪽 |
| `confirm_limit` | 같은 문의 통화에 그날 확정 전화를 2통 걸었음 | 그 통화만 |
| `window_passed` | 방문 시간(대)이 모두 지났거나 영업시간과 겹치지 않음 | 그 통화만 |

**세는 기준**: 접수한 날이 아니라 **전화가 나가는 날**입니다(저녁에 접수해 다음 날 9시에 나가는 통화는 다음 날 수). 거절됐거나 공급사 오류로 한 번도 걸지 못한 통화는 세지 않습니다.

## 발신 순서

- 서버는 **한 번에 한 통만** 겁니다. 묶음 안에서는 배열 순서, 묶음끼리는 접수 순서입니다. demo 모드에서는 시연 번호로만 거므로(번호가 하나면 모든 통화가 그 번호로) 겹치지 않습니다.
- 앞 통화가 **끊기면** 다음 통화를 겁니다(결과 추출은 기다리지 않음). `PHONE_AGENT_CALL_GAP_SEC`를 주면 끊고 그만큼 쉰 뒤 겁니다(한 번호로 시연할 때 숨 돌릴 시간).
- 받지 않았거나 자동응답이면 `retry_wait`가 되고 줄을 막지 않습니다. 30분 뒤 줄의 맨 앞에 다시 들어갑니다(1번만).
- 영업시간(월~토 9~19시, 공휴일 제외) 밖이면 `scheduled`로 두었다가 다음 영업 시작에 겁니다. 공휴일은 기본 목록에 `PHONE_AGENT_HOLIDAYS`를 더합니다.
- 차례가 왔을 때 방문 시간(대)이 모두 지나 있으면 걸지 않고 `failed`(`window_passed`)로 끝냅니다.

## 통화

- 공급사 에이전트의 고정 프롬프트와, 요청으로 만든 통화별 지시문으로 통화합니다([프롬프트](../prompts/agent_prompt.md)). 지시문의 `[이번 통화: 문의 …]` / `[이번 통화: 방문 확정]` 머리말로 통화 종류를 구분합니다.
- 지시문에는 `share`에서 허락한 정보만 넣습니다.
- **문의 통화**: 방·건물·층(호수)·가격·관리비·입주일을 묻고, 사용자의 가능 시간대 안에서 중개사가 되는 시간을 묻습니다. 약속은 확정하지 않습니다. 등기부를 보내 주겠다고 하면 "지금 전화드린 이 번호(살구 070 번호)로 문자 보내 주시면 됩니다"라고 안내합니다.
- **확정 통화**: "아까/어제 문의드렸던 살구"로 시작해, "그 방 아직 있죠?" 한 마디로 방을 확인하고(호수를 아직 모르면 "호수가 몇 호예요?"도), 요청 시각 → 대안 범위 순으로 맞춥니다. 범위 밖 시각은 받아 적기만 하고 확정하지 않습니다. 확정되면 날짜·요일·시각을 다시 말해 확인합니다. 같은 사무소의 방이 여러 개면 이른 방문부터 방마다 차례로 확인하고, 마지막에 방마다 되읽습니다.
- 사용자 연락처는 통화에서 말하지 않습니다. 통화 길이는 최대 180초입니다.

## 결과를 정하는 규칙

1. 대화록을 받아 화자를 나눕니다. "살구"(없으면 "AI 비서", "전화드린" 등)라고 소개한 쪽이 `ai`입니다. 소개를 못 찾으면, 첫 말이 "여보세요/○○부동산입니다"면 그 사람을 중개사로 봅니다.
2. LLM이 대화록에서 값과 **근거 줄 번호**를 찾습니다(문의·확정 프롬프트가 다름).
3. 코드가 대조합니다.
   - 근거 줄은 **중개사(`broker`)가 한 말**이어야 합니다. AI가 물어본 조건 줄은 근거가 아닙니다.
   - 금액·면적·건물·층·호수는 그 줄에 실제로 있어야 합니다. "3층", "2시"의 숫자는 금액으로 보지 않습니다.
   - 확정 시각은 예외가 하나 있습니다. 살구가 "11월 21일 토요일 오후 2시에 뵐 수 있을까요?"처럼 시각을 넣어 묻고 바로 다음 중개사 말이 거절이나 다른 시각 없이 "당연하죠/네/괜찮아요"면, 그 질문의 시각을 합의로 봅니다(근거 줄은 중개사의 대답, 날짜는 질문 줄로 확인).
   - 시각은 그 줄의 시·분으로, **날짜**는 그 줄(시각 바로 앞의 날짜 표현)이나 바로 앞 두 줄의 날짜 표현으로 확인합니다. 날짜 표현이 없으면 후보 날짜가 하나뿐일 때만 인정합니다.
   - **정정**: 근거 줄에 값이 있어도, 그 값 뒤에 고치는 말("아 잠깐만요", "아니다", "그건 옆방")과 비슷한 크기의 다른 값이 나오면(다음 중개사 말 두 줄까지) 고치기 전 값으로 보고 버립니다. AI가 말한 조건을 되풀이한 뒤 같은 말 안에서 다른 값을 말한 경우("천에 육십. 아, 천에 육십오야")와, 중개사도 확실하지 않은 값("오만이던가 칠만이던가")도 버립니다. 시각도 "2시는 힘들고 5시 어때?"처럼 그 시각을 거절하고 다른 시각을 말하면 인정하지 않습니다. 기록은 `corrections`에 남깁니다.
   - 확인되지 않은 값은 `null`로 비우고 `unverified`에 넣습니다.
4. 코드가 `outcome`을 정합니다. LLM의 판단(가능 여부 등)은 근거 줄이 있는 것만 씁니다.

**문의 통화**

| 조건 (위에서부터 먼저 맞는 것) | `outcome` |
|---|---|
| 두 번 걸어도 받지 않음, 자동응답 | `no_answer` |
| 중개사가 통화를 원하지 않음 | `declined` |
| 확인된 값이 하나라도 있는 방이 있음 | `listing` |
| 방이 없다고 함 | `no_listing` |
| 그 밖의 경우(방이 있다고만 하고 확인된 값이 없음 등) | `unclear` |

**확정 통화** (방마다 따로 정하고 `rooms[]`에 담음)

| 조건 (위에서부터 먼저 맞는 것) | 방별 `outcome` |
|---|---|
| 그 방이 나갔다고 함 | `unavailable` |
| 확인된 합의 시각이 그 방의 요청 시각이거나 대안 범위 안 | `confirmed` |
| 확인된 시각이 그 밖(합의했든 제안했든) | `alternative` |
| 방은 있다고 했지만 시각이 정해지지 않음 | `no_time` |
| 그 밖의 경우(어느 방 이야기인지 모름 포함) | `unclear` |

통화 전체: 받지 않음·거절이면 `no_answer`·`declined`(모든 방 같음). 아니면 모든 방 `confirmed` → `confirmed`, 일부만 → `partial`, 확정된 방이 없으면 `alternative` > `no_time` > `unavailable`(모두 나갔을 때) > `unclear`.

정정 감지는 방이 여럿일 때 다른 방이 같은 항목으로 가져간 값을 비교에서 뺍니다("해든빌라는 5만 원이고요, 아 참 새솔빌은 7만 원"에서 5를 버리지 않음).

## 알림

- 문의 묶음이 모두 끝나면 요약 한 번, 확정 통화가 끝날 때마다 한 번, 등기부 문자가 들어오면 한 번 보냅니다.
- 보내는 길: ① 카카오톡 '나에게 보내기'(`KAKAO_ACCESS_TOKEN`, 만료 시 `KAKAO_REFRESH_TOKEN`+`KAKAO_REST_API_KEY`로 한 번 갱신) → 실패하면 ② 문자(demo, `PHONE_AGENT_NOTIFY_TO` 또는 `PHONE_AGENT_DEMO_TO`). ③ mock이거나 설정이 없으면 기록만.
- 알림 실패는 통화 진행을 막지 않습니다. 결과의 `notifications[].status`에 남습니다.

## 등기부 수신

- 받는 번호는 **전화를 거는 살구 070 번호 하나**(`KAT_FROM_NUMBER`)입니다. 통화에서 그 번호를 불러 줍니다.
- 주기 작업이 30초마다 공급사의 수신 문자 목록(`GET /messages?status=received`)을 읽어 새 문자를 통화에 연결합니다.
  - 보낸 번호로 최근 7일 안에 건 통화를 찾습니다. 시연에서는 모든 통화가 한 번호로 가므로, "보내 주겠다"(`will_send`)고 했고 아직 받지 않은 가장 최근 통화를 먼저 고릅니다.
  - 연결하지 못한 문자도 수신함에 남깁니다.
- 본문의 주민등록번호는 바로 가립니다. 첨부 파일은 서버에 저장하지 않고, 요청이 올 때 공급사에서 받아 그대로 넘깁니다.

| 값 | 동작 |
|---|---|
| `mock` (기본) | 전화·문자를 보내지 않고 정해진 결과를 돌려줍니다. 요청 헤더 `X-Mock-Scenario`에 쉼표로 통화별 결과를 적을 수 있습니다. 문의: `listing`, `two_rooms`(방 두 개), `registry`(등기부 MMS가 들어옴), `no_listing`, `no_answer`, `voicemail`, `declined`. 확정: `confirmed`, `shifted`(대안 범위 시작으로 확정), `alternative`, `no_time`, `unavailable`, `partial`(첫 방만 확정, 나머지는 제안), `no_answer`, `declined`. |
| `demo` | 실제로 겁니다. `brokers[].phone`은 쓰지 않고 `PHONE_AGENT_DEMO_TO`의 시연 번호로만 겁니다. 번호가 하나면 모든 통화가 그 번호로, 쉼표로 여러 개 적으면 문의는 묶음 안 사무소 순서대로 돌아가며(1번→첫 번호, 2번→둘째 번호…), 재발신은 처음 건 번호로, 확정은 그 문의 통화를 받은 번호로 겁니다. 알림 문자는 첫 번호(또는 `PHONE_AGENT_NOTIFY_TO`)로 갑니다. |
| `live` | `brokers[].phone`으로 겁니다. 해커톤 범위 밖이며 만들지 않습니다. |

## 진행 확인(폴링)

- 웹훅은 쓰지 않습니다. 서버 안의 주기 작업(5초)과 조회 요청이 공급사 상태를 읽어 옵니다.
- 같은 통화는 `poll_interval_sec`(3초)보다 자주 공급사에 묻지 않습니다. 화면이 1초마다 조회해도 공급사 호출은 3초에 한 번입니다.

## 저장과 보관

- 통화·묶음·알림·등기부 수신 기록을 `.data/calls.json`에 저장합니다(mock은 저장하지 않음).
- 대화 전문은 `keep_transcript`가 `true`일 때만, 통화 종료 후 30일(`PHONE_AGENT_TRANSCRIPT_DAYS`)까지 둡니다. 근거 줄(`quotes`)은 남깁니다.
- 녹음은 받지 않습니다. 공급사 발신 번호의 녹음 설정은 공급사 대시보드에서 꺼야 합니다(아래 미확인).
- API 키, 발신 번호, 허용 번호, 카카오 토큰은 로컬 `.env`에만 둡니다.

'확인'은 2026-11-18의 API 호출과 시험 통화 4건(허용 번호로 발신)으로 본 것입니다.
